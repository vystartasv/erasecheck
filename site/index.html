THE CHECK, IN ORDER

Make forgetting testable.

EraseCheck is a small harness around your own test environment. Your app owns the setup, deletion and inspection logic.

01

Plant a canary

A fresh random string is written through your normal test setup path. It contains no user data.

02

Call deletion

Your adapter invokes the same application deletion callback your integration test is meant to exercise.

03

Inspect named stores

Each configured store returns a validated clear/residue finding. Cleanup waits for every inspection to settle, even when one fails.

↳

Why draw this boundary? An application can inspect only the stores and deletion paths it controls and configures. Provider-internal storage and retention are outside this check.

SCOPE IS A FEATURE

A check of your app.
Nothing broader.

— It does not claim legal compliance.

— It cannot verify provider-internal abuse logs.

— It says nothing about stores you did not configure.

— A passing run is evidence from one test environment, not a universal guarantee.

START WITH YOUR TEST ENVIRONMENT

Three callbacks.
One useful check.

Point EraseCheck at an adapter module. Use synthetic test data and test-scoped credentials. The required test environment prefix is a label check, not production protection. Adapter callbacks control their own network and data handling; the harness does not transmit the canary or report.

adapter.mjsES MODULE
export default {
  environment: 'test-local',
  adapter: {
    setup: async ({ canary }) => seedTestData(canary),
    erase: async ({ canary }) => deleteTestData(canary),
    cleanup: async ({ canary }) => purgeTestData(canary)
  },
  stores: [
    { name: 'primary-db', inspect: checkDatabase },
    { name: 'vector-memory', inspect: checkIndex }
  ]
};

node src/cli.mjs run ./adapter.mjs
